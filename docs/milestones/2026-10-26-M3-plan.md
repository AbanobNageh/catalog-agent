# M3 Write tools: Plan

**Goal:** three write tools, `create_product`, `set_price` and `set_stock`, on M1's `CatalogClient` and M2's tool layer. Each has `expectedVersion` and `dryRun` where §4.2 asks, annotations, and the §4.3 errors. `CATALOG_ACCESS=read|write` decides whether they exist. There are MCP-level tests in both eras, and integration tests through the real stdio server for every §4.3 row that can be caused.

**Spec:** `REQUIREMENTS.md` §4.1 (`CATALOG_ACCESS`), §4.2 (the write rows), §4.3, §4.4 (writes through the tools), §4.5 (the write tests), and the M3 row of §7. Design: [ADR-0006](../adr/0006-write-tools.md) (Proposed; accepted at the close). Builds on [ADR-0004](../adr/0004-catalog-client-reliability.md) and [ADR-0005](../adr/0005-mcp-tool-results-and-errors.md).

**Docs checked (2026-10-26):**
- **The 2026-07-28 spec:** the "Tools" page (the tool list may vary by authorization, never per connection) and `schema.ts`'s `ToolAnnotations`, with its defaults and meanings.
- **SDK 2.4.0's `ToolAnnotationsSchema`:** the same five fields.
- **`npm view`:** 2.4.0 is still the latest SDK, and zod 4.6.7, so ADR-0002's pins stand.
- **catalog-api `v1.1.0` at the tag:**
  - the create and update DTOs (no maximum string lengths, so `/docs-json` shows none)
  - `if-match.ts`: versions 1 to int32 max
  - `products.service.ts`: every `PATCH` raises the version
  - search-service's `query/build.go`: `q` searches `name^3` and `description` only
- **A research round on 13 well-known MCP servers' source,** summarised in ADR-0006. The AI checked seven key citations again itself.

**The user's choices (2026-10-26):**
- **`CATALOG_ACCESS`** defaults to `write`, set in `.env`. The AI had recommended `read`.
- **`set_price` / `set_stock`:** `destructiveHint: true`, `idempotentHint: true`.
- **A no-op set call** is a success with nothing sent.
- **The create hint** is reworded so a model can follow it.

**MCP terms used here** (defined in the code comments as well):
- **`destructiveHint`:** a hint that a tool may overwrite or delete something. False means it only adds.
- **`idempotentHint`:** a hint that calling the tool again with the same arguments changes nothing more.
  - Hosts use both hints for approval prompts and retry decisions, and must treat them as untrusted.
- **dry run:** the tool does everything a real call does except the write, and reports what it would change.
- **read-only mode:** the server registers only its read tools, so the write tools aren't in `tools/list` at all.

## Global constraints
- **Test-first:** every test is seen failing before the code that makes it pass. `npm run typecheck` after every change.
- **No delete, no reindex:** nothing reaches `DELETE /products/:id` or `POST /admin/reindex`. The admin key appears only in the test fixtures' cleanup.
- **Writes are never blindly retried.** Create isn't retried at all. A set call's only retry is ADR-0004's, inside `updateProduct`.
- **Isolation (§4.5):** the integration tests write only their own products, in category `it-<runid>-<suite>`. No test writes a `SEED-*` product.
- **No key, stack trace or upstream body** in a tool result, a log line or an error message.
- **stdout is the protocol;** logs go to stderr.
- **Commits** only at the close, after the user's yes.

## Review Focus
1. **No write without the user's intent.**
   - `dryRun: true` sends no `PATCH`, on every path. A unit test counts requests; an integration test re-reads the product and finds its version and value unchanged.
   - A no-op sends no `PATCH`.
   - `create_product` is never retried, and after a timeout its hint is the reworded one.
2. **`CATALOG_ACCESS`:**
   - `read` registers exactly the three read tools; a call to a write tool fails as an unknown tool, and nothing reaches catalog-api.
   - `write` (and unset) registers all six, in a stable order.
   - An invalid value fails at startup with exit 1, naming the variable, not its value.
3. **The version checks:**
   - a stale `expectedVersion` gives `STALE_VERSION` with the current version, from both the first read and the `PATCH`'s 412 (a write that lands between them)
   - a dry run checks the version too
   - confirm-after-timeout (ADR-0004) reaches the tool result as `confirmedAfterTimeout: true`
   - the new version is in every successful result
4. **Only the intended field is sent:** the `PATCH` body is exactly `{ "priceCents": n }` or `{ "stock": n }`, never another field and never `undefined`. The create body has no unknown fields, and no `currency` key when it's left out.
5. **The schemas match catalog-api,** and the contract check covers the write tools: field names, `required`, the integer bounds, and the deliberate differences (`currency`'s pattern, `expectedVersion`, `dryRun`).
6. **Every §4.3 row through the write tools,** each with its code, `retryable` and hint, text only (ADR-0005), with no key, stack or body in the result. The ones that can be caused are tested end to end (Task 7).
7. **The output shapes** match their `outputSchema` in all three cases (a dry run, an applied change, a no-op), and the summary line says which one happened.
8. **Annotations** as in ADR-0006, checked in `tools/list`.

### Task 3: The write schemas (test-first)
**Files:** `src/mcp/schemas.ts`, `src/mcp/schemas.test.ts`.
- **`createProductInput`** (strict):
  - `sku`, `name`, `category`, `brand`: strings, at least 1 character
  - `description`: any string
  - `priceCents`, `stock`: integers from 0 to 2147483647
  - `currency`: optional, `^[A-Z]{3}$`
- **`setPriceInput` / `setStockInput`** (strict):
  - `id`: a UUID
  - `priceCents` or `stock`: integers from 0 to 2147483647
  - `expectedVersion`: an integer from 1 to 2147483647
  - `dryRun`: a boolean, required, with no default
- **`setPriceOutput` / `setStockOutput`:** a flat object (ADR-0006).
  - `dryRun`, `id`, `sku`, `name`
  - `current`: the values now (after the write, if one was applied)
  - `version`: the version now, to send as `expectedVersion` next
  - **dry run only:** `proposed` and `wouldChange`
  - **applied only:** `previous`, `changed` and `confirmedAfterTimeout`
  - The values are `{ stock }`, or `{ priceCents, price, currency }`.
- **`create_product`'s output** is M2's `productOutput`.
- Tests: each bound at its edge and one past it, missing `dryRun` and missing `expectedVersion`, `currency` `egp`/`EG1`/`EGPP`, and unknown fields (`delta`, `version`).

### Task 4: The set tools (test-first)
**Files:** `src/mcp/tools/conditional-set.ts` (the shared flow), `src/mcp/tools/set-price.ts`, `src/mcp/tools/set-stock.ts`, `src/mcp/tools/annotations.ts`.
- **The flow** (ADR-0006):
  1. `getProduct`
  2. a version other than `expectedVersion` → `STALE_VERSION` with `currentVersion`, using catalog-api's message form
  3. `dryRun: true` → the preview
  4. the value already there → `changed: false`
  5. otherwise `updateProduct(id, { field: value }, expectedVersion)`, with `confirmedAfterTimeout` passed through
- **Summary lines:**
  - **a dry run:** "Dry run: stock of <name> (<sku>) would go from 4 to 50. Nothing was written. To apply it, call set_stock with dryRun: false and expectedVersion 3."
  - **a dry run with nothing to change:** "… is already 50; set_stock would change nothing"
  - **applied:** "Stock of … set from 4 to 50; now version 4.", plus "(confirmed after a timeout)" when it was
  - **a no-op:** "… is already 50; nothing was written (still version 3)."
  - `set_price` gives both forms: "799.00 EGP (79900)".
- **Descriptions** say:
  - to call `get_product` first and send its `version`
  - absolute values only, in integer cents for the price
  - do a dry run first, and apply only after the user agrees
  - what `STALE_VERSION` means

### Ledger of rulings (the AI's calls; the user can overrule any)
1. **`dryRun` is required** on the set tools, with no default, so every call is an explicit choice. It isn't on `create_product`: §4.2 asks for it on the set tools only, and a create preview couldn't check whether the SKU is taken.
2. **A dry run checks `expectedVersion` too,** and gives `STALE_VERSION` when it's out of date, so a preview says whether the real call would go through.
3. **Every set call reads the product first,** for the version and no-op checks. The worst case rises to about 57 s at the default timeout (ADR-0006).
4. **The version is checked before the value,** so a stale call is `STALE_VERSION` even when the value happens to match. The model's view is out of date, and its hint says to re-read.
5. **A write's result carries the new version.** Search hits have no version, so `get_product` stays the source for a first write.
6. **`currency` is `^[A-Z]{3}$`,** stricter than catalog-api's `IsUppercase` plus length 3, which allows digits. It goes on the contract check's deliberate list.
7. **No maximum string lengths,** because catalog-api has none, and §4.2 asks for the same bounds as the API.
8. **The outcome-unknown hint is set per tool** (Task 2), not inferred from the error, because the client's error doesn't say which operation it came from.
9. **A flat output object** with mode-specific optional fields, rather than a union: an `outputSchema` whose top level is `anyOf` is less portable across clients (Inspector's `--strict`).
10. **`CATALOG_ACCESS=write` with the read key is allowed.** The API's 403 is the second layer, and §4.5 tests it.
