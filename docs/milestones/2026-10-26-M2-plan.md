# M2 MCP server, read tools: Plan

**Goal:** a stdio MCP server with three read tools, `search_products`, `get_product` and `list_facets`, built on M1's `CatalogClient`. It works in MCP Inspector and in Claude Code through `.mcp.json`, has MCP-level tests in both protocol eras, integration tests through the real stdio server, and a contract check against catalog-api's `/docs-json`.

**Spec:** `REQUIREMENTS.md` §4.1, §4.2 (the read tools), §4.3 (the error shape), §4.5 (MCP-level, integration and contract parts), §4.6 (`.mcp.json`), and the M2 row of §7. Design: [ADR-0005](../adr/0005-mcp-tool-results-and-errors.md) (Proposed; accepted at the close). Builds on [ADR-0004](../adr/0004-catalog-client-reliability.md).

**Docs checked (2026-10-26):** the SDK v2 docs at https://ts.sdk.modelcontextprotocol.io/v2/ (tools, errors, stdio, testing, protocol versions, the 2026-07-28 migration guide), the 2026-07-28 spec's "Tools" page, and the SDK 2.4.0 code itself. A throwaway spike confirmed both eras in-process, the JSON Schema Zod produces, and error results with `structuredContent`. `npm view`: 2.4.0 is still the latest SDK, so ADR-0002's pins stand. Installed: `@modelcontextprotocol/server@2.4.0` and `zod@4.6.7` (dependencies), `@modelcontextprotocol/client@2.4.0` (dev).

**The user's choices (2026-10-26):** text content is a summary plus the JSON; MCP-level tests in both eras; the SDK's schema rejections accepted as a documented exception to §4.3; `search_products` returns `hasMore` and `nextPage`. All as recommended.

**MCP terms used here** (defined in the code comments as well):
- **tool:** a named function the server offers. The model sees its name, description and `inputSchema` (a JSON Schema) in `tools/list`, and calls it with `tools/call`.
- **`outputSchema` / `structuredContent`:** the JSON Schema of a tool's machine-readable result, and that result.
- **annotations:** hints about a tool's behaviour for the host (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). Hosts use them for approval prompts. They're hints, not enforcement.
- **transport:** how JSON-RPC messages travel. Here, stdio: the host starts the server as a child process and talks over its stdin and stdout.
- **era:** the 2025 protocol (an `initialize` handshake) or 2026-07-28 (stateless, with a `_meta` envelope on each request).

## Global constraints
- **stdout is the protocol.** Nothing but JSON-RPC ever goes to stdout: not at startup, on a config error, or on any tool path. Logs go to stderr through `src/log.ts`.
- **Test-first:** every test is seen failing before the code that makes it pass. `npm run typecheck` after every change.
- **`npm test` stays stack-free.** MCP-level tests run in-process against a `CatalogClient` with a scripted fake `fetch`. The stdio and integration tests are `*.int.test.ts`.
- **Read tools only.** No write tool, and nothing that reaches `DELETE` or reindex. `CATALOG_ACCESS` is M3.
- **Isolation (§4.5):** integration tests create their own products in category `it-<runid>-<suite>` and delete them with the admin key. Nothing writes a `SEED-*` product.
- **No key, stack trace or upstream body** in a tool result, a log line or an error message.
- **Commits** only at the close, after the user's yes.

## Review Focus
1. **stdout carries only JSON-RPC,** on every path: startup, a config error (exit 1, message on stderr), tool errors, and read retries that log. The stdio test checks every stdout line by parsing it, not by lint.
2. **No key, stack or upstream body in a tool result.** A test drives every error path and checks each result's text and `structuredContent` for the key, `    at ` stack frames and the raw body.
3. **The schemas match catalog-api exactly,** and the contract check really catches drift: a mutation (for example `size` max 100 → 101, or a `sort` value removed) must fail it.
4. **Error results** have `isError: true`, **no `structuredContent`**, and the §4.3 object `{ code, message, retryable, hint, details? }` as JSON in the text (ADR-0005, decision 5). The object is built from a `CatalogError`'s fields only. Any other thrown value becomes `INTERNAL` with a fixed message.
5. **Pagination:** `hasMore` and `nextPage` on the last page, on an exact multiple of `size`, with zero results, and at the 10,000 window.
6. **Money:** formatted with integer arithmetic (`0`, `5`, `79900`, `1999999`, int32 max), never floats.
7. **Both eras are exercised for real:** each MCP-level and stdio test checks `client.getProtocolEra()`.
8. **The per-tool-call log line** has tool, correlation id, duration, outcome, code, requests and retries, and never the key.
9. **`.env` loading:** variables already set win, a missing `.env` is fine, and it works from any working directory.

### Task 1: Per-call stats in the client (test-first)
**Files:** `src/catalog/client.ts`, `src/catalog/client.test.ts`.
- `CallContext` gets an optional `stats: { requests: number; retries: number }` that `send()` fills in: `requests` +1 per HTTP request, `retries` +1 when `retry > 0`. The tool layer passes one per tool call and logs it (carried from M1, M6).
- Tests: a read with 2 retries counts 3 requests and 2 retries; a failed read still fills the stats; an update's re-read counts.

### Task 2: Money and tool results (test-first)
**Files:** `src/mcp/money.ts`, `src/mcp/results.ts`, and their tests.
- `formatPrice(cents, currency)` → `"799.00 EGP"`, with integer arithmetic, two minor digits and no thousands separators.
- `toolSuccess(summary, data)` → `{ content: [{ type: 'text', text: summary + '\n\n' + JSON }], structuredContent: data }` (ADR-0005).
- `errorData(err)` → the §4.3 object `{ code, message, retryable, hint, details? }`; `toolError(data)` → `isError: true` with the same text form and no `structuredContent` (changed during the build; see the build record). One test per row of §4.3, with the hints:
  - `VALIDATION`: the API's messages
  - `UNAUTHORIZED`: "the MCP server's catalog key is missing or wrong (configuration problem)"
  - `FORBIDDEN`: the API's scope message
  - `NOT_FOUND`: "check the id; use search_products to find it"
  - `SKU_EXISTS`, `STALE_VERSION` (with the current version), `UNAVAILABLE` ("temporary; retry later"), `INTERNAL`
  - `details.outcome: 'unknown'`: "the change may have been applied; read the product before retrying"
- A value that isn't a `CatalogError` gives `INTERNAL` with a fixed message, never its own message or stack.

### Task 3: Schemas (test-first)
**Files:** `src/mcp/schemas.ts`, `src/mcp/schemas.test.ts`.
- **Shared filters:**
  - `q`: 1–200 characters
  - `category`, `brand`: at least 1 character
  - `minPrice`, `maxPrice`, `maxStock`: integers from 0 to 2147483647, in cents for the prices
  - `inStock`: boolean
  - `maxPrice ≥ minPrice`, as a refine
- **`search_products` adds:**
  - `sort`: enum from `SEARCH_SORTS`
  - `page`: from 1, default 1
  - `size`: 1–100, default 10
  - `includeFacets`: default false
  - `page × size ≤ 10,000`, as a refine
- **`get_product`:** `id` is a UUID.
- **Every input object is strict:** an unknown argument is rejected, not silently dropped.
- **Output schemas:** the compact hit, the full product (with `price`), and the facets.
- Tests: each bound at its edge and one past it, the refines, a strict-object rejection, and the defaults.

### Task 4: The tools and the server (test-first)
**Files:** `src/mcp/server.ts` (`createServer({ client, logger })`), `src/mcp/tool-call.ts` (the wrapper), `src/mcp/tools/search-products.ts`, `get-product.ts`, `list-facets.ts`.
- **The wrapper** gives each call a correlation id and a stats object, times it, turns any thrown value into `toolError`, and writes one `tool call` log line (Review Focus 8).
- **`search_products`** (`GET /products/search`):
  - compact hits: `id`, `sku`, `name`, `category`, `brand`, `priceCents`, `price`, `currency`, `stock`
  - plus `total`, `page`, `size`, `hasMore`, `nextPage?`, and `facets` only with `includeFacets`
  - the summary line gives the range shown and the next step (ADR-0005)
- **`get_product`** (`GET /products/:id`): the full product plus `price`. The description says to read it before changing a product, and that `version` is what a write must send back.
- **`list_facets`** (search with `size=1` and the filters): `total`, plus categories (top 20), brands (top 50) and price buckets (cents), each with counts.
- **Descriptions** say when to use each tool and when not to, and give the units ("priceCents: integer cents; 79900 = 799.00 EGP"). They also say that search hits can be stale and carry no version.
- **Annotations:** `readOnlyHint: true`, `openWorldHint: false` (a closed catalogue, not the open web). `destructiveHint` and `idempotentHint` are left out, because the spec gives them meaning only when `readOnlyHint` is false.

### Task 5: MCP-level tests in both eras
**Files:** `src/testing/mcp.ts` (`connect(era, server)` → `Client`), `src/mcp/server.test.ts`.
- **2025 era:** `InMemoryTransport.createLinkedPair()`. **2026-07-28:** `createMcpHandler(factory).fetch` behind a `StreamableHTTPClientTransport`, pinned. Each test runs in both, through `describe.each`, and checks `getProtocolEra()`.
- **What's checked:**
  - the tool list: exactly the three names, with their annotations and schemas
  - `search_products` and `get_product` return the right `structuredContent`, and the text is the summary plus the same JSON
  - a 404 gives `isError` with `NOT_FOUND`
  - a 503 retried twice still succeeds, and the log line says 2 retries
  - `size: 150` and an unknown argument give the SDK's validation text
  - Review Focus 2's sweep for the key, stack frames and the body

### Task 6: The entry point
**Files:** `src/main.ts`, `src/env.ts` (`loadDotEnv(path)`), `src/env.test.ts`, `package.json` (`start`), `.env.example`.
- **`.env`:** loaded from the repo root (`new URL('../.env', import.meta.url)`) when it exists, with `process.loadEnvFile`. Variables already set win.
- **Startup:** `loadConfig(process.env)`. On failure, the message goes to stderr and the process exits 1.
- **Serving:** `serveStdio(() => createServer(...))`. On SIGINT and SIGTERM, `handle.close()`.
- `npm start` = `node dist/main.js` (after `npm run build`).

### Task 7: stdio tests
**Files:** `src/mcp/stdio.int.test.ts`, `vitest.config.ts` (an `int` global setup that runs the build).
- **stdout purity:** spawn `node dist/main.js` and drive it by hand. The 2025 `initialize`, then `tools/list`, a good search, a 404, and a call that times out and retries (a fault proxy that hangs). Every stdout line must parse as a JSON-RPC 2.0 message; the logs must appear on stderr.
- **A config error:** exit code 1, the message on stderr, and stdout empty.
- **Both eras:** `StdioClientTransport`, connecting once with the default handshake and once pinned to 2026-07-28. `tools/list` and one call each.

### Task 8: Integration through the real stdio server
**Files:** `src/mcp/tools.int.test.ts`.
- The fixtures create products in `it-<runid>-tools` with chosen stock values.
- **Checks:**
  - `search_products` with the category, `maxStock` and `stock_asc` gives the expected order and compact fields

  - `get_product` gives the full product with `version` and `price`

### Task 9: The contract check
**Files:** `src/mcp/contract.int.test.ts`.

  - each search-only parameter exists in the API
  - the fields our outputs take from the API are `required` in `SearchHitResponse`, `ProductResponse` and `FacetsResponse`
- **Mutation-checked:** `size` max 101, a missing `sort` value, and `q` max 201 must each fail it.

### Ledger of rulings (the AI's calls; the user can overrule any)
1. **`.env` is loaded in code** (`process.loadEnvFile` on the repo root's `.env`), not with `node --env-file-if-exists=.env` as first proposed. A host may start the server from another working directory, and the relative path would then miss the file.
2. **Strict input objects:** an unknown argument (a model sending `limit` instead of `size`) is rejected, not silently dropped.
3. **Explicit int32 bounds:** a bare `z.int()` advertises ±2^53, but catalog-api's integers stop at 2147483647.
4. **`size` defaults to 10**, not the API's 20, for smaller outputs (§4.2). Stated in the description.
5. **Annotations:** `readOnlyHint: true`, `openWorldHint: false`, and no `destructiveHint` or `idempotentHint` (see Task 4).
6. **`get_product` checks the UUID format,** so a bad id fails before it's sent (catalog-api would answer 400 `Validation failed (uuid is expected)`).
7. **The full §4.3 error mapping is built now,** including the write codes' hints, because the read tools already need the shape. M3 tests the write rows through the write tools.
8. **The retry count reaches the tool log through a stats object** in `CallContext`, not by changing every client method's return type.
9. **Prices are formatted with two minor digits and no separators** (`19999.00 EGP`): all catalogue data is EGP, and the format matches §4.2's example.
10. **The stdio tests are in the `int` project,** whose global setup runs `npm run build`, because they spawn `dist/main.js`. CI's `integration` job already runs `test:int`.
11. **The server's name and version** are constants in `src/mcp/server.ts` (`catalog-agent`, `0.0.0`, the same as `package.json`). M4 bumps both.
12. **TypeScript 7 hides `bin/tsc` behind its export map,** so the `int` global setup finds it next to `typescript/package.json` and runs it with the current Node.
13. **`.mcp.json` runs `node dist/main.js` with a relative path.** Claude Code's docs don't say which working directory a stdio server starts in; this is checked in the Claude Code demo. `.env` doesn't depend on it, because `main.ts` finds the file by its own location.

### Build record (2026-10-26)
Tasks 1–9 are built, and Task 10 except the Claude Code check.
- **Unit,** before the review: 206 tests in 11 files (`npm test`, under 1 s, no stack). The MCP-level suite runs every test in both eras.
- **Integration,** before the review: 37 tests in 6 files (`npm run test:int`, about 65 s): M1's 20, plus 4 stdio, 7 tool and 6 contract tests.
- **After the review fixes:** 210 unit tests in 11 files, and 42 integration tests in 7 files (3 `.env` tests, 2 more contract tests).
- **Test-first:** every new test was seen failing first, except for Task 6. `src/main.ts` was written before its stdio test, so the stdio test is proven by mutation instead (below).
- **Mutation checks** (each applied, the tests run, then reverted):
  - a `process.stdout.write` in `main.ts`: the raw-pipe stdio test fails ("not JSON on stdout"). **The SDK's own `StdioClientTransport` tolerates the stray line,** so only the raw test can catch it.
  - contract: `size` max 101; `q` max 201 (caught in both tools); `newest` removed from `sort`
  - `nextPage` set past the 10,000 window: caught in both eras
  - a non-catalog error's own message copied into the result: caught
- **Inspector 2.12.0 (CLI mode, reading `.mcp.json`):**
  - `tools/list` passes with `--strict` (no schema portability problems)
  - `tools/call search_products` returns the expected text and `structuredContent`
  - with catalog-api replaced by a socket that never answers, Inspector waited the full 15.3 s of a read's worst case (3 × 5 s timeouts plus backoff), so its timeout needs no change
- **Found by the demo check, and re-decided with the user:** Inspector validates `structuredContent` against `outputSchema` even on `isError` results, and rejected our first error results. The research (in ADR-0005) showed that well-known servers return text-only errors. The user chose JSON in the text, with no `structuredContent` (ADR-0005, decision 5). It was changed test-first: `errorOf()` in the tests rejects an error result that has `structuredContent`. Inspector now shows the error.
- **Claude Code (the user, in a new session, 2026-10-26):** the `catalog` server connected through `.mcp.json` after `.env` was created, so a relative `dist/main.js` works and Claude Code starts project servers in the repo folder. Asked for low-stock books and the first one's details, the model called `search_products` (`category=books`, `maxStock=5`, `sort=stock_asc`), then `get_product` on the first hit's id. It reported `total: 118`, `hasMore: true`, `nextPage: 2`, the price as "889.00 EGP (priceCents 88900)" and version 1, and noticed on its own that the stock-0 ties come back in id order. Still unknown: whether Claude Code passes the text block, `structuredContent` or both to the model on a success, because all three fields it quoted appear in both. **The error path** (`get_product` on the all-zero UUID): the model received the text-only error, quoting its summary line, hint and JSON (`NOT_FOUND`, `retryable: false`). It explained that the result was a tool error rather than a protocol error, and offered to search instead.
- **Found by the hand smoke test:** with stdin piped from a file, the response to the last request never arrived. The SDK drops in-flight requests when stdin reaches end-of-file (documented). So the raw stdio test keeps stdin open until every answer is in.

### Mistakes caught during the build
- `main.ts` was written before its test (above).
- **The AI's Claude Code instructions were wrong:** they said the session would use "the read key from the defaults", but `CATALOG_API_KEY` has no default, and the repo had no `.env`. The server exited at startup with "CATALOG_API_KEY is required" (on stderr), and Claude Code showed only "Failed to reconnect to catalog: CONNECTION_CLOSED".
