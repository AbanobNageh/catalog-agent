# M1 Catalog client: Plan

**Goal:** one typed HTTP client for catalog-api `v1.1.0` that the tools (M2, M3) will use, never calling `fetch` themselves. It has timeouts, read retries with jittered backoff, conditional writes that are confirmed after a timeout instead of blindly retried, typed errors, and structured stderr logs.

**Spec:** `REQUIREMENTS.md` §4.4, §4.3 (the codes; the hints are M3), §4.5 (unit and integration parts), and the M1 row of §7. Design: [ADR-0004](../adr/0004-catalog-client-reliability.md) (Proposed; accepted at the close).

**The user's choices (2026-10-26):** a fault proxy plus one real search-service pause; after the retry's 412, re-read and confirm again; our own small logger.

## Global constraints
- **No MCP code yet.** The client is plain TypeScript with no new dependencies: Node 24's `fetch` and `AbortSignal.timeout`, `node:http` for the proxy, `node:crypto` for ids.
- **Test-first:** every test is seen failing before the code that makes it pass.
- **`npm test` stays stack-free** (unit tests only, as in CI's `check` job). Integration tests are `*.int.test.ts`, run by `npm run test:int` against the Compose stack, one file at a time.
- **Isolation (§4.5):** every integration test creates its own products in category `it-<runid>` and deletes them afterwards with the admin key. Nothing ever writes a `SEED-*` product.
- **The key never reaches a log line, an error, a result or a test snapshot.**
- **Commits** only at the close, after the user's yes.

## Review Focus
1. **No double write, in any branch.** Every confirm-path test checks the end state through a fresh `GET`: the version is exactly `expectedVersion + 1` (never +2), and the values are the target ones.
2. **What's never retried:** a 4xx, a 5xx other than 503, any `POST`. And a `PATCH` only through the confirm path, at most once.
3. **The confirm check is exact:** the target fields compared one by one, and the version `=== expectedVersion + 1`, not `>=`. A product at `expectedVersion + 2` with the target values is `STALE_VERSION`.
4. **The retry's 412 is re-checked** (ADR-0004, decision 3): our own late first attempt is reported as confirmed, not as a conflict.
5. **Timeouts cover the response body,** not only the headers: a server that sends headers and then stalls still times out.
6. **The key is never logged or echoed:** a test records every log line and error message in a full confirm-path run and asserts the key isn't in any of them; the logger redacts credential-like field names.
7. **Backoff:** the delays are within `[0, min(2000, 200 × 2^n))`, there are at most 2 retries, and the unit tests use the injected clock, so they wait for nothing.
8. **The fault proxy is trustworthy:** it has its own tests against a local dummy server, and the pause test always unpauses search-service, even when it fails.
9. **CI:** the `check` job is unchanged and stack-free; the new `integration` job builds the stack from `v1.1.0` and runs `npm run test:int`.

### Task 1: Logger (test-first)
**Files:** `src/log.ts`, `src/log.test.ts`.
- `createLogger({ write?, level? })`: one JSON line per call, `{ time, level, msg, ...fields }`, to `process.stderr` by default. `write` is injectable for tests. Levels `debug` < `info` < `warn` < `error`.
- Fields named like credentials (`/authorization|api[-_]?key|token|secret|password/i`, at any depth) are written as `"[redacted]"`.
- Tests: the JSON shape; level filtering; redaction (top-level and nested); the default writes to stderr, never stdout (spy on both).

### Task 2: Config: `CATALOG_TIMEOUT_MS` (test-first)
**Files:** `src/config.ts`, `src/config.test.ts`, `.env.example`.
- Default 5000; a whole number from 100 to 60000; the error uses the API's own wording style (`CATALOG_TIMEOUT_MS must be a whole number from 100 to 60000`). `CatalogConfig.timeoutMs`.

### Task 3: Errors (test-first)
**Files:** `src/catalog/errors.ts`, `src/catalog/errors.test.ts`.
- `CatalogError extends Error { code, status?, retryable, details? }`, with codes `VALIDATION`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `SKU_EXISTS`, `STALE_VERSION`, `UNAVAILABLE`, `INTERNAL`.
- `fromResponse(status, bodyText, { op })`, one test per row of §4.3:
  - 400 joins a `message` list with `; `
  - 409 is `SKU_EXISTS` only for `op: 'create'` (otherwise `INTERNAL`)
  - 412 is `STALE_VERSION`, `retryable: true`, `details.currentVersion` from the body
  - 503 is `UNAVAILABLE`, `retryable: true`
  - anything else is `INTERNAL`
  - a non-JSON or huge body gives a message cut to 500 characters, never the raw body
- `fromNetworkError(err)`: a timeout (`TimeoutError`/`AbortError`) or a connection error (`TypeError` from `fetch`) is `UNAVAILABLE`, with `details.cause` (`timeout` or the system code, for example `ECONNREFUSED`). Matched by `name`, as product-catalog does, because fetch's errors come from Node's own realm.

### Task 4: Backoff and read retries (test-first)
**Files:** `src/catalog/retry.ts`, `src/catalog/retry.test.ts`.
- `backoffDelay(attempt, random)` = `random() × min(2000, 200 × 2^attempt)`.
- `withReadRetries(fn, { clock, random, maxRetries: 2 })` retries only an `UNAVAILABLE` `CatalogError`, and reports how many retries it made.
- Tests: the delay bounds at random = 0 and ≈ 1; success after 1 and after 2 retries; giving up after 2 (3 calls); no retry on `NOT_FOUND`, `VALIDATION`, `INTERNAL`; the fake clock recording the sleeps.

### Task 5: The client (test-first)
**Files:** `src/catalog/types.ts`, `src/catalog/client.ts`, `src/catalog/client.test.ts`.
- `new CatalogClient({ baseUrl, apiKey, timeoutMs, fetch?, clock?, random?, logger? })`. Methods take an optional `{ tool, correlationId }` call context:
  - `search(params)`: `GET /products/search`, with only the defined parameters sent
  - `getProduct(id)`: `GET /products/:id`
  - `createProduct(input)`: `POST /products`, never retried
  - `updateProduct(id, fields, expectedVersion)`: the conditional `PATCH` with the confirm path from ADR-0004, returning `{ product, confirmedAfterTimeout, attempts }`
- Every request: `Authorization: Bearer`, `Accept: application/json`, JSON bodies, `AbortSignal.timeout(timeoutMs)` covering the body read, and one log line.
- Unit tests with a scripted fake `fetch`:
  - the URL, headers and query building, with `If-Match` exactly `"<n>"`
  - read retries happen for `GET` only
  - create: a timeout gives `UNAVAILABLE` with `details.outcome: 'unknown'` and exactly one `POST`
  - **the confirm table:**
    - landed → confirmed
    - not landed → retry → 200
    - not landed → retry → 412 → re-read shows ours → confirmed
    - not landed → retry → 412 → someone else → `STALE_VERSION`
    - not landed → retry times out → still not landed → `UNAVAILABLE`
    - a concurrent write → `STALE_VERSION`
    - at +2 with our values → `STALE_VERSION`
    - gone → `NOT_FOUND`
    - re-read fails → `UNAVAILABLE` (`outcome: 'unknown'`)
    - a first-attempt 412 → `STALE_VERSION` with no re-read
  - the log lines carry tool, correlation id, method, path, status, duration, retries and code, and never the key (Review Focus 6)

### Task 6: The fault proxy (test-first)
**Files:** `src/testing/fault-proxy.ts`, `src/testing/fault-proxy.test.ts`.
- `startFaultProxy(upstreamUrl)` → `{ url, next(fault), close() }`. It passes requests through to the upstream, except for the faults queued with `next`, one per request:
  - `'hang'`: never forward, never answer (the request "never arrived")
  - `'cutAfterForward'`: forward, wait for the upstream's full response, then never answer (the write "landed, response lost")
  - `{ status: 503 }`: answer itself, without forwarding
- Tests against a local dummy `node:http` server: pass-through (method, path, headers, body, status), each fault, and that `close()` frees the port.
- `src/testing/` is excluded from the build (`tsconfig.build.json`).

### Task 7: Integration tests
**Files:** `src/testing/fixtures.ts`, `src/catalog/client.int.test.ts`, `src/catalog/confirm.int.test.ts`, `src/catalog/pause.int.test.ts`, `vitest.config.ts` (projects `unit` and `int`), `package.json` (`test`, `test:int`).
- Fixtures: a run id; create products in category `it-<runid>` with the write key; delete them all with the admin key in `afterAll`.
- `client.int.test.ts` (no faults):
  - search with `category=it-<runid>`, `maxStock` and `stock_asc`
  - get, then an update: version +1
  - a planted concurrent update: `STALE_VERSION` with the current version
  - create with a duplicate SKU: `SKU_EXISTS`
  - read key on a `PATCH`: `FORBIDDEN`
  - an unknown key: `UNAUTHORIZED`
  - a random id: `NOT_FOUND`
  - a bad body: `VALIDATION`
- `confirm.int.test.ts` (through the proxy):
  - `cutAfterForward` → confirmed after timeout
  - `hang` → retry → success
  - `cutAfterForward` plus a planted concurrent write → `STALE_VERSION`
  - two 503s on a `GET` → success with 2 retries
  - three → `UNAVAILABLE`
  - a create that `hang`s → `UNAVAILABLE` with an unknown outcome, and exactly one product with that SKU exists afterwards, or none
  - Each checks the end state with a fresh `GET` (Review Focus 1).
- `pause.int.test.ts`: with a client timeout of 1000 ms, `docker compose pause search-service`, update a product, `docker compose unpause search-service` in a `finally`. The client reports `confirmedAfterTimeout: true`, and a fresh `GET` shows version +1.
- `npm run test:int` runs files one at a time (`fileParallelism: false`).

### Task 8: CI integration job and commands
**Files:** `.github/workflows/ci.yml`, `AGENTS.md`.
- A job `integration` (after `check`): checkout, Node 24, `npm ci`, `docker compose up --build -d --wait`, `npm run test:int`, and `docker compose logs` on failure. It runs on the same triggers for now; whether it stays on every pull request is decided when its run time is known (M4, §6).

### Ledger of rulings (the AI's calls during the build)
1. **Lint fails on warnings** (`--deny-warnings`). Three type-aware warnings in this milestone would otherwise have passed CI; oxlint exits 0 on warnings.
2. **`SearchParams` accepts an explicit `undefined`,** which is left out of the query. With `exactOptionalPropertyTypes`, the tools would otherwise have to strip optional arguments themselves.
3. **One log line per HTTP request** (op, method, path without the query, `retry`, status or code and cause, duration), plus a `conditional update` summary line (attempts, `confirmedAfterTimeout`, the version). A `retry` field was added after re-reading §4.4, which asks for the retry count; it was missing from the first version.
4. **After the retry also fails and the product is still at `expectedVersion`:** `UNAVAILABLE` with `outcome: 'unknown'`, not "not applied", because either attempt may still be in flight upstream. A `not_applied` outcome was drafted and removed.
5. **Fixtures use plain `fetch`, not the client under test,** and find a suite's products through the paged list (Postgres), not search, so they work while search-service is paused.
6. **Integration test timeouts:** 3000 ms through the proxy; 1500 ms for the pause test, between a normal write (about 1 s) and a paused one (about 2 s), with a control write first. See the mistake below.
7. **The retry's own 412 (Review Focus 4) is covered by unit tests only.** Driving it end to end needs a first attempt that lands *after* the client's re-read, which the proxy can't time reliably.
8. **A CatalogError carries `retries`,** so the logs and the tools can say how many retries a failed read made.

### Mistakes caught during the build
- **The first pause test could pass for the wrong reason.** It used a 1000 ms client timeout, but a normal write takes about 1005 ms (search-service's `refresh=wait_for`), so the write would have "timed out" with or without the pause. It surfaced as a flaky failure in a proxy test at the same timeout. The AI's first explanation, Vitest running the pause file first, was wrong: catalog-api's and search-service's logs showed every index write taking about 1 s. Fixed with the timeouts above and a control write, which a 900 ms mutation now proves effective. ADR-0004 records the latency.
- `npm test` passed while `tsc` failed twice (`exactOptionalPropertyTypes`), because Vitest strips types without checking them. Typecheck now runs after every change, as CI does.

### Fresh review (2026-10-26): findings and re-grades
A separate agent reviewed the whole uncommitted diff, read-only, against `REQUIREMENTS.md`, this plan, ADR-0004 and catalog-api's code at `v1.1.0`. It ran every test suite, made probes on its own `review-` products (deleted afterwards), and tried mutations on a copy. It found no double-write path, no loop and no blind retry, and reported 1 Important and 13 Minor findings, with no Critical ones.
- **I1, kept Important, fixed test-first:** after an ambiguous first `PATCH`, two paths reported a plain failure even though the first attempt could still land: a re-read that got a 500, and a retry that got a 500, 400, 403 or 409. M3 would have told the model "failed, don't retry" for a write that may apply. Now every later error except `NOT_FOUND` and `STALE_VERSION` is `UNAVAILABLE` with `outcome: 'unknown'`. 4 new tests.
- **M1, Minor, half fixed:** a no-op change, after a timeout, can be "confirmed" over someone else's write to another field, because catalog-api raises the version on a no-op (checked live by the reviewer). An empty change is now refused before sending (test-first); skipping no-op writes is carried to M3 (`wouldChange`); ADR-0004 documents the limit.
- **M2, fixed:** a 409 on update (a `PATCH` that changes the sku to one another product has) is now `SKU_EXISTS`, not `INTERNAL`; the comment claiming only create can 409 was wrong.
- **M3, fixed in ADR-0004:**
  - the backoff waits total at most 0.6 s, not "about 3 s"
  - a response can come up to about 3 s after its commit (the Redis calls add 1 s), not 2 s
  - the claim that the proxy drives "every branch" contradicted ruling 7
  - the Redis cache-aside on `GET /products/:id` is now described, with why it's safe for the re-read
  - the worst case of one conditional update, about 41 s at the default timeout, is now stated
- **M4, re-graded Important and fixed:** the plan claimed a test for "no key in error messages", but only log lines were checked. The reviewer showed it by putting the key in every network error message, and all tests still passed. A new test checks the message and details of four failure paths.
- **M5, fixed test-first:** a non-JSON 2xx body escaped as a raw `SyntaxError` quoting the body. It's now `INTERNAL`, with the outcome unknown after a write.
- **M6, half fixed:** `outcomeUnknown` reset the retry count; now it's copied. Returning the retry count of a successful read is carried to M2's per-tool-call log.
- **M7, fixed:** `passWithNoTests` inside a Vitest project is ignored (it's a root-only option). Removed, since tests exist. `vitest.config.ts` isn't typechecked (tsconfig covers `src/` only), which is why nothing flagged it.
- **M8, fixed:** `AGENTS.md` now names the `integration` CI job. STATUS's "load `.env`" item moves to M2, which has the first entry point.
- **M9, fixed test-first:** the proxy turned an unreachable upstream into an unhandled rejection, and assigned faults when a body finished arriving. Now the socket is closed and the fault is taken on arrival.
- **M10, carried:** products from a killed integration run (`it-<runid>-*`) are never cleaned up. A sweep command is a follow-up.
- **M11, fixed test-first:** the logger's redaction matched any name containing `token`, `key`… and would have hidden Phase 2's `prompt_tokens`. It now matches whole names.
- **M12, no change:**
  - the "never logged a key" integration tests read lines from earlier tests in their file, so they don't work alone under `-t`
  - the proxy close test's first assertion is weak, but `close()` would hang without `closeAllConnections`
  - the pause test's margins are about ±0.5 s: on a slow runner its control write fails loudly, never falsely
- **M13, carried to M2/M3:**
  - MCP request timeouts must allow the ~41 s worst case
  - tools must not pass `undefined` inside `changes`
  - tool results are built from the error's fields, never the `Error`
  - any `TypeError` maps to `UNAVAILABLE` (harmless now that config checks the key format)
- **One more mistake by the AI while fixing these:** it wrote the new tests with a shell heredoc and a Python search-and-replace, against `AGENTS.md`'s rule. The replacement silently didn't match, because Prettier had reformatted the file. The edits were redone with the Edit tool.
